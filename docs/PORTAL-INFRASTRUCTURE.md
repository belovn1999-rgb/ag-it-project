## 2. Целевая архитектура

```
Сотрудник (браузер, belovn1999-rgb.github.io/ag-it-project — адрес сайта не меняем, §4.4)
   │  личный ключ сотрудника в заголовке Authorization
   ▼
api.<домен>  = Cloudflare Worker «ag-api»  (Cloudflare: Worker + Durable Objects + D1)
   ├─ /proxy?url=…     → белый список хостов → лимит и очередь портала → кэш → портал
   │                     (otomoto, Blocket, AutoScout24, Marktplaats, 2dehands,
   │                      Kleinanzeigen, av.by, будущие willhaben/ParuVendu…)
   ├─ /mobilede/…      → постоянный туннель (named tunnel) → Chrome-узел → mobile.de
   ├─ /monitoring/…    → задания и записи Monitoring в базе D1, у каждого сотрудника свои
   ├─ /me, /admin/keys → кто вошёл; владелец выдаёт и отзывает ключи
   └─ журнал запросов (кто, портал, сколько, ошибки)

Chrome-узел = всегда включённый компьютер с обычным интернетом (Mac mini в офисе;
пока его нет — Mac владельца)
   ├─ импортер mobile.de 127.0.0.1:8788 — настоящий Chrome, как сейчас
   ├─ cloudflared named tunnel → chrome.<домен> (пускает только Worker, §3.3)
   └─ раннер Monitoring: берёт задания у api.<домен>, проверяет, отдаёт записи туда же
```

Что где работает:

| Портал / задача | Где читается | Почему |
|---|---|---|
| otomoto, Blocket, AutoScout24 (все страны), Marktplaats, 2dehands/2ememain, Kleinanzeigen, av.by | **Worker-прокси** (B11) | защиты от ботов нет, нужен только CORS; Worker бесплатен и быстрый. Какие порталы пускают Cloudflare — по замерам чата B11; не пустивший остаётся на `r.jina.ai` или идёт через Chrome-узел |
| mobile.de (объявление, поиск, детали) | **Chrome-узел** через туннель | mobile.de отказывает серверам, прокси и headless Chrome, пускает настоящий Chrome с обычного интернета (§4.3.1) |
| La Centrale, Leboncoin | **нигде автоматически** | проверено 10-05: DataDome блокирует и Chrome импортера; правило проекта — защиту не обходим (`PORTALS-EXPANSION.md` §3 п. 6). Только закладка в браузере менеджера или партнёрский доступ |
| Monitoring 9:30 | **раннер на Chrome-узле** | ему нужен mobile.de (Chrome), остальные порталы он читает тем же Worker-прокси |
| Задания, записи, позже избранное и история | **база D1** за Worker | личные данные сотрудника, проверка владельца на сервере (B26) |

Почему не один VPS для всего: Worker дешевле и надёжнее для простых порталов, а для
mobile.de VPS не помогает — с адреса датацентра mobile.de не пускает (§6, вариант В).

## 3. Безопасность

### 3.1 Доступ только для сотрудников — личные ключи

- **Этап 1 — личный ключ сотрудника.** Владелец в `/admin/keys` создаёт ключ на имя
  (например «Nikodem»), сотрудник один раз вставляет его на странице («Klucz dostępu
  AUTOGOOD»), браузер хранит его в `localStorage` и шлёт в заголовке. Worker хранит
  только хэш ключа (SHA-256) с именем и флагом «активен». Ключ можно отозвать в любой
  момент, не трогая остальных.
- Без ключа или с отозванным ключом страница **не ломается**: работает как сейчас
  (`r.jina.ai`, без mobile.de с сервера) и показывает «Brak klucza — wolniejszy tryb».
- Проверка `Origin` остаётся, но это не защита (её подделывает любой скрипт) — защита
  именно ключ.
- **Почему не «вход через Google/почту» сразу.** Cloudflare Access (бесплатно до 50
  человек) даёт настоящий вход, но его cookie живёт на домене API, а сайт — на
  `github.io`: Safari и Firefox такие «чужие» cookie режут, Chrome — по настройке пользователя.
  Вход через Access — когда сайт переедет на свой домен (§4.4), с переносом данных.
- Личный ключ = аккаунт для B26: сервер сам определяет сотрудника по ключу и не верит
  имени или id, присланному браузером (`AUTOGOOD_SERVER_DEPLOYMENT.md`).

### 3.2 Секреты вне репозитория (репозиторий публичный)

| Секрет | Где живёт |
|---|---|
| хэши ключей сотрудников | база D1 (не в коде) |
| ключ владельца для `/admin`, токен доступа Worker → туннель | секреты Worker (`wrangler secret` / панель Cloudflare) |
| учётные данные туннеля, ключ раннера | на Chrome-узле: `~/Library/Application Support/AUTOGOOD/*.env`, права 600 |
| аккаунт Cloudflare | у владельца, с двухфакторным входом; Claude паролей не вводит |

В репозитории — только код и `server/.env.example` с **именами** переменных.

### 3.3 Белый список и узкие двери

- Прокси: только `https`, только `GET/HEAD`, только хосты из списка (уже есть в
  Worker B11), ответ не больше ~5 МБ, таймаут ~20 с, к порталу не уходят cookies и
  `Authorization` сотрудника, `Set-Cookie` портала не возвращается.
- Импортер на Chrome-узле слушает только `127.0.0.1`. Туннель `chrome.<домен>` закрыт
  Cloudflare Access «service token»: его знает только Worker. Сотрудник никогда не
  ходит на Mac напрямую — только через Worker с ключом.
- Лимит на ключ (например 1 500 запросов в час): утёкший ключ не забанит нам порталы.

### 3.4 Защита от бана IP

- **Одна очередь на портал для всех сотрудников** — в Durable Object (один «счётчик»
  на портал в Cloudflare) вместо очереди в каждом браузере. Пример стартовых лимитов
  (уточнить замерами B11): otomoto 30/мин, AutoScout24 30/мин, Blocket 30/мин,
  Marktplaats/2dehands 20/мин, Kleinanzeigen 15/мин, av.by 10/мин; не больше 3
  одновременных запросов к порталу. Запрос сверх лимита ждёт в очереди до ~20 с, потом
  `429 Retry-After` — браузер повторит.
- **Пауза портала после отказа**: 429/403 от портала → портал на паузе 2 → 5 → 15 мин
  для всех, страница пишет «otomoto: przerwa do 10:42», не долбит дальше.
- **Кэш одинаковых поисков** (§5) — повтор того же поиска не идёт на портал.
- mobile.de: одна вкладка Chrome-узла, ~1 запрос в 1–2 с, своя очередь (как сейчас).

## 4. Данные пользователей (§4.6.1 — не теряются никогда)

1. Браузер остаётся источником: ничего локального не удаляется и не заменяется.
2. Сервер только **добавляет**: записи Monitoring сервера приходят в браузер через
   существующий `importRecords` (только добавление, `MONITORING-SERVER.md` §2).
3. Перенос избранного и истории на сервер — отдельным явным шагом «Zapisz kopię na
   serwerze» после ключа: слить, не перезаписывать, дубли убрать без потерь, отчёт о
   конфликтах; локальная копия остаётся.
4. **Адрес сайта не меняем** без переноса данных: `localStorage` привязан к адресу —
   переезд с `github.io` на свой домен «потерял» бы избранное у всех. Если когда-то
   переезжать — сначала серверная копия (п. 3), потом переезд, потом загрузка копии.

## 9. Риски и открытые вопросы

- OPEN: пускают ли порталы запросы из Cloudflare Worker (у таких запросов заметный
  адрес Cloudflare) — ответ даст замер B11. Портал, который не пустит, остаётся на
  `r.jina.ai` или идёт через Chrome-узел (с тем же темпом).
- Автоматическое чтение mobile.de с настоящего Chrome — то, что работает сейчас; если
  mobile.de начнёт блокировать и его, решение — партнёрский доступ, не маскировка.
- Один Chrome-узел — одна точка отказа для mobile.de; при сбое остальные порталы
  работают, страница пишет «mobile.de niedostępny».
- Лимиты бесплатного плана Cloudflare: 100 000 запросов в день хватает на ~10–20
  активных сотрудников; дальше — $5/мес.
