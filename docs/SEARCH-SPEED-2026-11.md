## 5. Почему проверка мониторинга идёт 44–133 с (шаг 3, разбор без правок)

Чтение порталов на стенде не замеряется (сборщик без сети), поэтому разбор — по коду `MonitoringRunner` и замерам сервера
25–26.10 (`PLATFORM-SEARCH.md` §4е).

**Как идёт проверка сейчас.**

1. Основные списки: до 3 порталов одновременно (`zrok.monitoring.parallel_reads`, очередь `portals-monitoring`, 3 процесса
   Horizon), каждый портал — одним чтением целиком (`full`). Портал, который та же подборка читала тем же адресом меньше часа
   назад, берётся копией (`adoptRecent`, 3б.18) — без запроса.
2. **Барьер.** «Blisko filtrów» начинается, только когда дочитаны **все** основные порталы (`step`: `if ($mainBusy) return`).
   План строится один раз по ответившим порталам.
3. Узкие поиски: у каждого портала с выдачей < 20 машин (3б.19) — до 8 видов (пробег ↑↓, мощность ↑↓, год ↑↓ на границе
   поколения, цена ↑↓, оснащение — выборкой). Одновременно — до 3, **но по одному на портал**: если малых порталов 1–2, они
   идут почти по очереди (у подборки 14 на сервере — 40 узких чтений, 2dehands один давал ≈ 95 из 110 с до 3б.21).
4. Дочитывание: факты объявлений, которых портал не проверил сам (`fillFacts`, до 40 за шаг), затем оснащение новых
   и избранных машин (`fillEquipment`, по 3 за шаг, до 20 за проверку, до 60 в день на портал) — страницы объявлений
   по одной, с паузами портала.
5. Каждое чтение — два шага очереди (шаг проверки и само чтение); после 3б.22 очередь просыпается сразу.

**Где время (сервер, 25–26.10):** подборка 14 (10 порталов) — 122–133 с → 110 с (3б.18–3б.20) → 83 с (3б.21) → 44 с
