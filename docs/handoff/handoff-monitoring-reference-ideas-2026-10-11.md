# Handoff: идеи из похожих проектов для Monitoring (стр. 3 `mobile.html`)

> Для нового чата группы «mobile». Дата: 2026-10-11. Источник идей —
> [`docs/REFERENCE-PROJECTS.md`](../REFERENCE-PROJECTS.md) §2 (пункты M…).
> Все пункты — **HYPOTHESIS**: сначала проверка, потом короткий отчёт владельцу,
> реализация — только после его «да».

## 0. Перед работой (обязательно)

1. Прочитай `docs/PROJECT_BRAIN.md`, `docs/PROJECT-MOBILE.md` §0 и §2 (правила
   параллельных чатов), §4.6.1 (данные пользователя не теряются никогда), §4.6.3
   (как устроен Monitoring), `docs/MONITORING-SERVER.md`, `docs/PORTAL-INFRASTRUCTURE.md`.
2. `git fetch` и `git status -sb`. Работай в своём `git worktree` от `origin/main`:
   в основной копии лежат чужие незакоммиченные правки.
3. **Код чужих проектов не копируем.** У deal-finder, used-car-deal-finder, cenomierz
   и avby-bot лицензии нет — берём только идею и пишем своё.
4. Ключи, токены, пароли — только в настройках службы на Mac / сервера, **не в репозитории**
   (он публичный). Фикстуры тестов — без имён и телефонов продавцов.
5. Говори с владельцем просто, без терминов; в конце каждого пункта — «что нужно от вас».

## 1. Порядок работы по каждому пункту

1. **Проверка у источника** — открой ссылку на GitHub, прочитай указанные файлы,
   ответь: как это работает у них, на каких данных, какие ограничения.
2. **Проверка у нас** — найди указанные места в коде, опиши, что уже есть.
3. **Вердикт** — пригодится ли точно, где именно, что даст менеджеру. Если у нас уже
   есть равноценное — так и скажи, пункт закрывается без кода.
4. **План внедрения** — файлы, данные, решения владельца, критерии готовности.
5. После «да» — реализация, тест, `ship`, строка в журнал `PROJECT-MOBILE.md` §7 и
   `PROJECT_BRAIN.md` §8, статус пункта в `REFERENCE-PROJECTS.md`.

Рекомендуемый порядок: **M15 → M9–M10 → M3 → M2 → M1 → M17 → M14 (только решение)**.
M4 и M13 — см. §4 (не внедрять).

## 2. Пункты

### M15 — стоп портала после отказа

- **Источник:** [Dropio12/used-car-deal-finder](https://github.com/Dropio12/used-car-deal-finder)
  — README, раздел про сборщик: «одна страница за раз, ≥ 1,5 с между запросами по всем
  сайтам; если сайт хоть раз сказал нет — прогон этого сайта останавливается»;
  [max286674-cpu/avby-bot](https://github.com/max286674-cpu/avby-bot) — `avby_bot_local.py`,
  `waf_check()` и `check_cooldown()`: после 403/423/468 пауза 2 ч (файл-метка).
- **У нас:** `src/market-proxy-queue.js` — `worker.strikes[host]`, отказ (403, 429, 5xx,
  страница-блокировка `BLOCK_PAGES`) передаёт запрос на `r.jina.ai` (`handOn`); план B73 —
  `PORTAL-INFRASTRUCTURE.md` §3.4 «пауза портала 2 → 5 → 15 мин, 403 — без повторов».
  Отображение «brak odpowiedzi» у молчащего портала уже есть (B74).
- **Проверить:** что происходит, когда **оба** пути (Worker и r.jina.ai) получают отказ —
  сколько ещё запросов уходит к этому порталу в том же прогоне (по коду и пробным
  прогоном с подменой ответа 403).
- **Внедрить (если повторы есть):** после N отказов подряд с обоих путей — портал
  «на паузе до HH:MM» до конца прогона (Monitoring и анализ), остальные запросы к нему
  не отправляются; на плитке — «portal odmówił, pauza do …». Для службы Mac — пауза
  переживает перезапуск страницы (запись в её папке).
- **Зачем:** бережём доступ к порталам — один бан otomoto/Kleinanzeigen стоит дороже
  одной пропущенной проверки.
- **Готово, когда:** при подменённом 403 к порталу уходит не больше N запросов за прогон;
  остальные порталы работают; плитка честно пишет причину.

### M9–M10 — проверка парсеров каждый день + тесты на сохранённых ответах

- **Источник:** [danyk20/deal-finder](https://github.com/danyk20/deal-finder) —
  `deal_finder/adapters/base.py` (`health_check()` у каждого портала), `tests/fixtures/*.json`
  + `tests/test_adapters_*.py` (разбор без сети); [Michal-w-pl/cenomierz](https://github.com/Michal-w-pl/cenomierz)
  — README, функция `health`: раз в час, письмо админу при сбое, раз в сутки пока сбой
  длится, и письмо после починки; Dropio12 — «ни один тест не ходит на живой сайт».
- **У нас:** `.github/workflows/ci.yml` (офлайн-аудит фильтров), `release-smoke.yml`
  (только вручную), тесты `scripts/market-listing.test.mjs`, `duplicates.test.mjs`,
  `monitoring-budget.test.mjs`, `offer.test.mjs` — проверь, на чём они: на сохранённых
  страницах порталов или на собранных руками объектах.
- **Внедрить:**
  - **M10 (первым):** `scripts/fixtures/<портал>/` — по 1–2 настоящих ответа каждого
    портала (otomoto `__NEXT_DATA__`, AutoScout24 `__NEXT_DATA__`, Marktplaats/2dehands
    `__CONFIG__`, Blocket, ParuVendu, Kleinanzeigen, av.by API JSON, ответ импортера
    mobile.de) **без персональных данных**; тест: цена, валюта, год, пробег, мощность,
    ссылка, страна, продавец, НДС. Каждая будущая поломка «под одну машину» → новый
    файл в фикстуры.
  - **M9:** GitHub Action по расписанию (утро до 9:30): один известный поиск на каждый
    портал через наш Worker → > 0 объявлений и все ключевые поля; падение Action =
    письмо владельцу (GitHub шлёт сам, как сейчас при падении CI). Проверь, пускает ли
    Worker запросы без заголовка `Origin` из Actions (`server/cloudflare-proxy/worker.js`,
    `ALLOWED_ORIGINS`) — не ослабляя защиту, иначе отдельный ключ в секретах Actions.
    mobile.de из облака не читается (только импортер на Mac) → его проверка — в службе
    Mac (`/monitoring/health`) с записью в лог.
- **Зачем:** портал меняет вёрстку — узнаём в 8 утра, а не от менеджера после пустой проверки.
- **Готово, когда:** `pnpm test` гоняет фикстуры всех порталов; Action падает, если
  поломать один парсер (проверь нарочно на ветке).

### M3 — статус «wróciło» (машину сняли и выставили снова)

- **Источник:** Dropio12 — README: Worker «помнит старые цены», классы **new / relisted /
  cheaper**, уведомление один раз на цену; [qwillemse/autoscout-analyser](https://github.com/qwillemse/autoscout-analyser)
  — README: `first_seen` / `last_seen` у объявления, история не удаляется.
- **У нас:** статусы строк Monitoring — `new`, `firstSeen`, `gone`, `outside`, `cheaper`,
  `dearer`, `same` (`src/mobile-market-analysis.js` ~5352, 5429; `src/mobile-monitoring.js`
  ~645); признаки «та же машина» — `src/duplicates.js` (цена ± пробег + год, тест
  `duplicates.test.mjs`); дни на рынке и снижения — B22.
- **Проверить:** бывает ли это на самом деле — пройди сохранённые проверки (IndexedDB
  `autogood-mobile-check-offers`) 2–3 избранных за 2+ недели: есть ли «новые» объявления,
  совпадающие с исчезнувшими раньше (тот же продавец/город, год, пробег ± 1 %, цена ± 10 %).
  Если за 2 недели ни одного случая — сообщи и закрой пункт.
- **Внедрить:** при появлении нового — поиск совпадения среди исчезнувших за 30 дней
  того же поиска → статус **«wróciło»** («zniknęło 12 dni temu, było 23 900 €»), дни на
  рынке — с первого появления. Только чтение старых записей (4.6.1).
- **Зачем:** перевыставление = машина плохо продаётся → аргумент для торга; «новая» на
  самом деле старая — менеджер не тратит время.
- **Готово, когда:** тест на искусственной паре «исчезло → появилось с новым номером»;
  на реальных данных ложных совпадений нет (проверить глазами 10 случаев).

### M2 — значок «okazja» (выгодная машина)

- **Источник:** Dropio12 — README, раздел о движке оценки: похожие = та же модель, близкий
  год, похожий пробег; база = цены дилеров, частники со скидкой; **сигнал при ≥ 15 % ниже
  базы и ≥ 6 похожих**; битые, на запчасти и «только лизинг» исключены.
- **У нас:** `liquidity(offer).deal` и фильтр результатов «deal» (`mobile-monitoring.js`
  ~1450–1455) — **сначала выясни, что это за правило** (возможно, M2 уже есть под другим
  именем); «poniżej P25» и «% к медиане» — `src/mobile-favorites-watch.js` ~728;
  «podejrzana cena» (×0,4 / ×2,5).
- **Внедрить (если «deal» — это не то же самое):** значок **«Okazja»** = цена «na gotowo»
  ≥ X % ниже медианы **похожих** (год ± 1, пробег ± 35 %, мощность ± 15 % — заодно M6),
  похожих ≥ 6; без «podejrzana cena» и красных слов (битый / на запчасти — словарь
  `offer-verdict.js`); при наведении — основание («−18 % od mediany 14 podobnych»).
  Порог X — решение владельца (предложить 10 и 15 %).
- **Зачем:** глаз сразу падает на лучшие варианты; на малой выборке громких выводов нет.
- **Готово, когда:** на 3 живых избранных значок у 0–3 машин, каждое основание сходится
  с ручным расчётом.

### M1 — уведомления о новых машинах

- **Источник:** deal-finder — `deal_finder/pipeline.py`: `_Run._enriched` (Telegram по одной

  9:30) возвращает **записи**, а «что нового» считается в браузере
  (`mobile-monitoring.js`, сравнение с прошлой проверкой того же поиска). Отправки
  писем/Telegram нигде нет (`src/offer.js` `sendMail` — другое).
- **Проверить:** может ли раннер получить готовый список «новые / подешевели / wróciło»

- **Решения владельца (спросить до кода):** канал — письмо (с какого ящика: info@autogood.pl

- **Внедрить:** в раннере после утренней проверки — сводка по каждому авто с
  мониторингом (фото, название, цена, «na gotowo», % к медиане, ссылка, кнопка «Otwórz w
  Monitoring»); «отправлено» — отдельный ключ на стороне службы (ключ объявления + цена),
  пишется **только после успешной отправки**; режим «Wyślij test» (всё как новое, без
  записи). Тот же канал потом нужен офферу (O1 — слежение после отправки).
- **Зачем:** сейчас новое видно, только если открыть стр. 3; менеджер узнаёт о выгодной
  машине раньше конкурента.
- **Готово, когда:** тестовое письмо/сообщение приходит; повторный прогон без изменений
  ничего не шлёт; при выключенном интернете в момент отправки сводка уходит в следующий раз.
